# Athena — Project Plan

Athena is a personal desktop companion for EVE Online. It reads two sources, the **ESI API** and the **local chat and game logs**, and shows the results in a modular dashboard of movable panels.

## Goals

- **Low resource use first.** It runs next to several EVE clients and should feel snappy, including the intel map. Targets, measured in step 2 and checked again after each module:
  - Idle CPU under 1% with the window open and nothing changing (no repaints while idle).
  - Minimized or unfocused: no repaints at all except when a module has new data to show.
  - RAM under 100 MB with the static data loaded.
- **Modular dashboard.** Modules are panels you can move, dock and resize. The layout is saved between runs.
- **Designed for a 1080p maximized window** (not fullscreen). Panels resize properly under Windows display scaling (for example 125%).
- **Portable on Windows.** Download a zip, unpack it and run the exe, with no installer. Everything except login tokens (settings, layout, cached data) lives in a folder next to the exe. Tokens stay in Windows Credential Manager, so moving the folder to another PC means logging in again. If the exe's folder isn't writable (for example under Program Files), Athena falls back to `%APPDATA%\Athena` and says so in the settings panel.
- **EULA-safe.** Athena only uses ESI and log files. It never reads client memory, injects into the client or automates input.

**Audience:** Kevin, possibly his corp later.

## Tech stack

| Area | Choice | Why |
|---|---|---|
| Language | Rust | No GC pauses or heavy runtime, a small single exe |
| UI | `egui` / `eframe` | Redraws only on change, GPU drawn, supports transparent always-on-top windows for overlays |
| Render backend | `glow` (OpenGL) by default; `wgpu` available behind the `wgpu` cargo feature until both are measured on Windows | `glow` is usually lighter; a 2D map doesn't need `wgpu` |
| Dockable panels | `egui_dock` (decided in step 2) | Tabs that can be docked, split, resized and pulled out into floating windows, with built-in `serde` support for saving the layout |
| Log watching | `notify` for new files + a cheap size poll of active files | Windows doesn't reliably raise change events for files another process keeps open |
| HTTP / ESI | `reqwest` (with `rustls`) + `tokio` | Async ESI calls; `rustls` keeps the exe free of extra TLS DLLs |
| Local storage | SQLite via `rusqlite` (bundled) | Static data and history in one file |
| Tokens | Windows Credential Manager via `keyring` | Refresh tokens are not stored in plain text |
| Config | `serde` + TOML | Human-readable settings and layout next to the exe (`data\settings.toml`, `data\layout.toml`) |

Considered and rejected: **Tauri** (WebView uses more memory), **C# / WPF** (large maps tend to feel sluggish).

## Data sources

### Local logs
- Default location: `Documents\EVE\logs\Chatlogs` and `...\Gamelogs` (configurable).
- **Encoding:** chat logs are UTF-16 LE, game logs are UTF-8. The parser handles both.
- **Watching:** a new file starts each session. `notify` catches new files; the currently active files are also polled for size every 250 to 500 ms, and only appended bytes are read. Verify the latency early in step 3 with a live client.
- **Multiple clients:** all clients write to the same folders. Each file's header names the character (`Listener:` in chat logs, the character line in game logs), and files are matched to characters through that header.
- **Character location:** the Local chat log writes `Channel changed to Local : <system>` on every jump. That is the primary location source (faster than ESI); the ESI location endpoint is only a fallback.
- Game logs contain combat, mining and notification lines (used by the Mining Supervisor).
- Intel channel lines get matched against system names, ship names and keywords from static data (see the Intel Supervisor below). Which intel channels to watch is a setting.

### ESI
- Register an application at developers.eveonline.com (Kevin does this, Athena never ships a secret).
- EVE SSO with **PKCE** and a localhost callback, with support for multiple characters.
- Send the `X-Compatibility-Date` header, respect cache headers and ETags, and read both the error-limit and the newer token-bucket rate-limit headers.

### Static data
- System names, IDs, positions and stargate connections from EVE's static data export, bundled as SQLite.
- Used for intel parsing, jump distances and drawing the map.
- **Map layout:** the Intel map's system positions come from DOTLAN EveMaps' region maps (see Step 6), with the SDE's `position2D` as the fallback.
- Built by a small `xtask` that converts the official SDE (in its current distribution format) into a compact SQLite with the game data Athena needs: ore types and their reprocessing (Mining Supervisor) and, for the Intel Supervisor, systems, constellations, regions, gates, positions and ship type names. It's re-run by hand or by a manual CI workflow after patches that change the map. The generated file is produced in CI and bundled into the release zip rather than committed, so the repo stays small.

### Step 2: Skeleton app and CI
- `eframe` window sized for a 1080p maximized layout, with DPI-aware sizing.
- Dockable panel layout with placeholder modules, and the layout saved/restored from the portable data folder.
- Settings panel (log folder path and similar).
- A small module trait so new modules plug in the same way.
- `windows_subsystem = "windows"` so no console window opens next to the app.
- GitHub Actions on `windows-latest`: `cargo fmt --check`, `cargo clippy -- -D warnings`, tests and a release build, uploaded as a zip artifact. Version tags (`v*`) create a GitHub Release with the portable zip.
- Measure idle CPU/RAM against the targets above with both render backends, pick one, and record the numbers as the baseline.
- Note in the README that the exe isn't code-signed, so Windows SmartScreen warns on first run ("More info" then "Run anyway").
- **Done:** `egui_dock` picked over `egui_tiles`. Baseline from the Linux sandbox (glow, software rendering under Xvfb): 0 CPU ticks over 30 s idle with the window open, so no idle repaints. RAM there (about 120 MB) is dominated by the software OpenGL driver and doesn't say much about Windows; the Windows numbers for both renderers are still open.

### Step 3: Data foundations
- Log watcher and parsers for chat and game logs, with unit tests from sample log lines. Fixtures taken from real logs are anonymized (character names, channel contents) before they're committed.
- ESI client with SSO (PKCE), token storage and multiple characters.
- **Done (public part):** `src/esi.rs` is a small blocking ESI client for background threads (`X-Compatibility-Date`, ETags, error-limit and 429 back-off). The Mining Supervisor uses it for Jita market orders. SSO and tokens come with the first module that needs a login.
- Static data import and lookup (systems, gates, jump routes).
- **Done (ore part):** `cargo xtask sde` reads the official SDE zip (JSON Lines format) and writes `static.sqlite` with every ore, ice, moon ore and gas type (volume, portion size, compressed type, reprocessing outputs) plus the materials they reprocess into. CI downloads the SDE (cached per SDE build) and ships the file next to the exe. Systems and gates get added to the same file for the Intel Supervisor.

### Step 4: First modules
- **Mining Supervisor:** for multiboxed miners, one row per character plus totals. Uses game logs, the SDE and ESI's public market data (no login).
  - Ore hold fill per character, split into uncompressed and compressed ore. The log has every mined cycle (including critical successes; residue is ignored as it never reaches the hold) and every in-space compression (1:1 in units). Unloading at a station writes no log line, so each row has an "Emptied" button. Hold size and alert level are global settings (default 11,500 m³ and 70%) that each character can override. Fullness comes from the m³ math, and EVE's own "cargo hold is full" line counts as full whatever the math says. EVE logs only the ore that fit, so nothing mined is lost.
  - Alerts: hold above a per-character threshold, hold full, miner stopped (the module's "deactivates" line, or no cycle for a while), idle for X minutes.
  - A session starts with the first mined cycle and ends only when Kevin clicks "End session", which ends it for all characters at once. History shows one entry per session that opens to per-pilot data. A finished session's ISK value (reprocessed value at Jita prices from ESI's public market data, cached and refreshed at most hourly; yield 90.63% for ore, ice and moon ore, 95% for gas) is stored once and never recalculated. History also shows daily and weekly totals.
  - Belt scan: Athena watches the clipboard for a copied Mining Survey Scanner result and shows m³ and rocks left, reprocessed value, the belt's mining rate (rolling, from the last two scans, so other miners count) and the time until the belt is cleared.
  - Covers all ore, ice and moon ore; volumes, compressed types and reprocessing outputs come from the SDE.
  - UI: a panel at most a quarter of 1080p wide. Compressed ore is purple; normal ore is green, yellow from the alert level, red when full. Mockups are shown to Kevin for approval before any panel is built.
  - **Done:** the panel follows the approved mockup (Live, History and Settings views). Settings live in `mining.toml`, the live hold and session state (with log file positions, so a restart neither misses nor double counts ore) in `mining_state.toml`, and finished sessions in `mining.sqlite`. A session can't be ended while no Jita prices are loaded, so its value is never frozen at 0. Days and weeks in History follow EVE time (UTC), weeks start Monday (confirmed by Kevin).
- **Intel Supervisor:** a RIFT-like region map with an intel list, faster and lighter than RIFT. Uses chat logs, static data and ESI's public endpoints (no login). Approved mockup: https://claude.ai/artifact/AAU2CByJPT4bJj9xbcFqeY (all names and numbers in it are made up, and its positions were placed by hand).
  - **Panel:** fits beside the Mining panel on a maximized 1080p window (about 1440 px wide). The map and the intel list sit side by side with a draggable split between them; the panel itself resizes like every dock tab. Two views: Map and Settings. Module id `intel`.
  - **Channels:** Settings lists the channels found in the Chatlogs folder, and Kevin ticks the ones to watch. Files are matched to a channel by the `Channel Name:` line in their header, not by file name, so the new file EVE starts after a relog or downtime is picked up on its own. Chat logs are UTF-16 LE, so the reader works differently from the UTF-8 game log reader: it skips the BOM, reads appended bytes in even counts (an odd trailing byte waits for the next read) and handles CRLF. Only appended bytes are read.
  - **One report, many files:** EVE writes a separate log for every character in a channel, so with four pilots in Branch Intel each report arrives four times. Lines are de-duplicated by (channel, sender, text) within a few seconds of each other; the same check drops a report pasted into two watched channels (then without the channel). Each report gives one list entry and at most one alert.
  - **Own pilots:** each character is placed on the map from `Channel changed to Local : <system>` in their Local chat log and shown in blue, with a chip per pilot in the toolbar. Only Local files started after the last downtime (11:00 UTC) count, so characters that haven't played for weeks don't show up; a pilot can also be hidden from their chip. Jump distance for alerts counts from the nearest shown pilot. "Follow" keeps the map on the active pilot's region and switches region when that pilot jumps out (setting, on by default). The active pilot is the one picked on the Follow button, by default whoever jumped most recently.
  - **Map:** one region at a time (picker in the toolbar), drawn like RIFT: a dot per system, the name on a small dark label to its lower right with the security status, the system's tags underneath, and gate lines between dots. Systems in neighbouring regions that connect by gate are drawn as hollow dots with dashed lines. Positions first came from the SDE's `position2D` (CCP's schematic layout, the same one as the in-game 2D map). Kevin found it too distorted, so Step 6 switches to Dotlan's hand-made layout. The xtask places each region and nudges overlapping labels apart once, so nothing is laid out at runtime. The region picker leaves out wormhole, Abyssal and other regions without gates or without `position2D` (PR 1 checks that every k-space system has one). Pan by dragging, zoom with the wheel, "Fit region" and zoom buttons. Smooth pan and zoom is a hard requirement: the map is drawn with egui's painter, skips anything off screen, and repaints only while it is being moved or when new data arrives.
  - **Report states:** a reported system's dot turns red with a "jumps · age" badge and its gate lines turn red. It fades from red through orange to grey over 10 minutes (setting). A message with a clear word ("clr", "clear", setting) turns it green. Fading needs no animation: the colour is worked out from the report's age whenever a frame is drawn, and while a report is fading the module asks for one repaint per 30 s at most, and not at all while Athena is minimized (new reports and alerts still repaint).
  - **Parsing a line:** `[ time ] Sender > text`. Words are matched against system names from static data (case-insensitive, full names plus unique prefixes of at least 3 characters, so "X7R" finds X7R-JW). Prefixes are looked up within the shown region, the regions of the own pilots, and the neighbours of both. Words are also matched against ship type names (from the SDE), "nv" (no visual) and the clear words. The remaining words, minus a small stop-word list of common intel words ("gate", "ratting", "nv" and the like are real character names too), form pilot-name candidates of one to three words, since EVE names have up to three. They're looked up with ESI's public `POST /universe/ids/` (at most 500 names per call; hits and misses are both cached), and the ones that are real characters become links to their zKillboard page. A line with no system in it is still listed, greyed out.
  - **Intel list:** newest first. Each entry shows time, system, jumps from the nearest own pilot, a ship chip when a ship type was reported, the clickable pilot names, the message text and the channel. An "Only in range" toggle hides reports beyond the alert range.
  - **Alerts:** a report within 5 jumps (setting) of any shown pilot plays a sound and shows a red banner across the top of the map with the system, the pilots it's close to, the ship and the reporter. Within 2 jumps (setting) the alert is loud: it plays at full volume whatever the volume slider says, and twice. "Mute 5 min" and "Dismiss" buttons. Settings chooses the sound: Voice (default) or Beep.
    - The voice lines are WAV files in a `sounds` folder next to the exe: "Enemy in system", "Enemy 1 jump", then "Enemy 2 jumps" and so on up to "Enemy 10 jumps" (the alert range setting goes up to 10). Kevin can replace any file with his own recording. If a file is missing, the beep plays instead.
    - The CI job makes them with the Windows built-in voice through `System.Speech`. That needs Windows PowerShell 5.1 (`shell: powershell`), not `pwsh`. The step fails the build if the runner has no voice installed, rather than shipping an empty folder.
    - Playback uses `PlaySoundW` (the `Win32_Media_Audio` feature of the existing `windows-sys` crate, no new crate). `PlaySoundW` has no volume control, so Athena loads each WAV once, scales its samples in memory by the volume slider, and plays the copy with `SND_MEMORY`; that changes only the alert, not other sounds. Sounds play synchronously on a background thread (so the second play of a loud alert isn't cut off), never on the UI thread.
    - Settings has a play button per file, the volume slider and a "flash the map and tab" toggle. As built, the flash draws a red frame around the map and flashes Athena's taskbar button (egui_dock tabs can't flash).
  - **Tags:** labels on systems, shown under the system name, with a colour, an icon and a group (for example `4DTQ-K;POS;#F5FF83;structure_skyhook;false;POS`). Import and Export use RIFT's text format through the clipboard, one tag per line (`System;Label;Colour;Icon;flag;Group`), so a RIFT export pastes straight in; fields Athena doesn't use (the `false` flag, unknown icon names) are kept and written back unchanged. Known icons get their own small symbol (`resources_isk`, `mining_diamond`, `structure_skyhook`), others a plain dot in the tag's colour. Right-clicking a system on the map opens a menu with "Add tag…", "Mark clear" and "Open on Dotlan" (opens the browser). The mockup's "Set as destination" is left out for now because it needs an SSO login with the `esi-ui.write_waypoint` scope; it comes back once Athena has SSO (see Later). Each tag group can be hidden on the map. Tags are saved in `intel_tags.txt` in the data folder, in the same format.
  - **ESI kills and jumps tint:** optional, off by default. Tints systems by ESI's public player kills of the last hour (jumps show on hover), fetched at most once an hour.
  - **Storage:** settings in `intel.toml`; tags in `intel_tags.txt`; reports are kept in memory only (they're old news after a restart, so nothing is saved).
  - **Static data:** the xtask adds regions, constellations, systems (name, security, `position2D`, region), stargate connections and ship type names to `static.sqlite`. Jump distances are a breadth-first search over the gate graph in memory, which takes well under a millisecond for the jump ranges used here.
    - **Done (PR 1):** `static.sqlite` schema version 2 adds `regions`, `constellations`, `systems`, `gates`, `region_borders` and `ship_types`. Only systems with stargates are kept (5,268 systems in 68 regions: known space, Pochven and Zarzakh); every one of them has a `position2D`, and the xtask fails if that ever changes. Each region's map is laid out once in the xtask: one grid step of `position2D` becomes 36 points at zoom 1.0 (Branch comes out about 920 × 800 points), and overlapping labels are nudged apart, mostly up or down. Systems of neighbouring regions are placed 64 points out from the system they connect to, in their real direction. `src/universe.rs` loads it; a 10-jump search from four systems takes about 15 µs in a release build.
    - Jumps count every gate as one jump, Zarzakh included; its gate lock (you can't jump back out the way you came for a while) doesn't matter for intel distances. Pochven and the Jove region UUA-F4 have no gates to the rest of space, so nothing there is ever "in range" of a pilot outside.
    - **Done (PR 2):** `static.sqlite` is loaded once at startup and shared by both modules (`modules::SharedStaticData`). The Intel module reads the chat logs (`src/modules/intel/`: `chatlog`, `watcher`, `dedupe`, `parser`), places own pilots from Local, lists the channels for the picker and keeps the reports in memory. Reports older than 10 minutes when Athena starts are skipped. Until the map arrives, the Map view is a plain list of pilots and reports.
    - **Done (PR 3):** the map (`src/modules/intel/map.rs`): dots, labels, gate lines, dashed lines to other regions, own pilots in blue with their names, pan, wheel zoom around the pointer, zoom buttons and "Fit region" (it refits when the panel resizes until the map is moved). Each region's shapes are built once when it's picked; off-screen shapes are skipped and text sizes are whole points. Labels are left out below zoom 0.55. Toolbar: region picker (all 68 regions; Pochven is kept for its own intel), Follow menu ("whoever jumped last" or a pilot), pilot chips that hide a pilot on click (`hidden_pilots` in `intel.toml`). The map and the list have a draggable split (`list_width`). Follow switches region only when the active pilot turns up in another region, so a region picked by hand stays until then. The shown region and its neighbours join the prefix scope. Security colours are EVE's, null sec in the mockup's red.
    - **Done (PR 4):** report colours and badges on the map (`alerts.rs`), the intel list as cards with the "Only in range" toggle, the alert banner with Dismiss, "Mute 5 min", sound playback (`sound.rs`), the Alerts box in Settings and the CI step that makes the voice WAVs. Jump distances are kept for systems up to 30 jumps from a shown pilot and rebuilt only when a pilot moves or is hidden. Reports read at start-up never alert, and the start-up cut-off follows the fade time. Pilot names aren't picked out in the list yet: the raw candidates are mostly ordinary words ("anyone around"), so they wait for PR 6, which checks them against ESI and shows only real characters as zKillboard links.
    - **Done (PR 5):** tags (`src/modules/intel/tags.rs`): RIFT-format import from the clipboard (copies of a tag already there are skipped) and export to it, saved in `intel_tags.txt`; icons are painted as shapes (Ƶ, diamond, triangle, dot) so they don't depend on fonts. Each tag shows under its system's name on the map. Right-clicking a system's dot opens "Add tag…" (a small window: label, group, colour, icon; it starts from the group last used), "Open on Dotlan" and "Mark clear" (a clear report from "You"). Settings lists the tags with a remove button and has the group filter (`hidden_tag_groups` in `intel.toml`). A late report that is older and further away no longer replaces a closer alert banner.
    - **Done (PR 6):** ESI lookups run on their own thread (`src/modules/intel/lookup.rs`), so the UI never waits on the network. Pilot-name guesses are gathered for half a second from the first one and sent to `POST /universe/ids` in batches of up to 500; each guess is asked about once per session. A guess that ESI knows becomes a zKillboard link in the intel list and the alert banner. Plenty of ordinary words and phrases are character names too ("anyone", "big blob", "be careful"), so a guess only counts when it is written exactly like the character, upper and lower case included, and has a capital letter (dragged names always qualify); a few more chat words joined the stop list. The kills and jumps tint (Settings › Map, off by default) fetches `/universe/system_kills` and `/universe/system_jumps` with ETags just after ESI's `Expires` time (at most once an hour), and only while it is on: a purple glow for ship and pod kills, growing with the log of the count (Kevin chose kills only, no glow for jumps, to keep the map calm); hovering a system shows its kills and jumps, and the legend gains "Kills (1 h)". Links open through Explorer on Windows.
  - **Build order (one PR each):** 1) static map data and jump distances; 2) chat log watcher, de-duplication, line parser, own-pilot locations and the channel picker, with anonymized fixtures; 3) map widget with pan, zoom, region picker, Follow and the pilot chips; 4) intel list, alerts, alert and sound settings, voice files and the CI step that makes them; 5) tags (import/export, right-click menu, group filter); 6) pilot lookup for zKillboard links and the optional ESI tint.

### Step 5: Overlays
Two Athena windows drawn on top of the screen. Only visible when EVE runs in *Window* or *Fixed Window* mode (Kevin uses Fixed Window). Mockup awaiting approval: https://claude.ai/artifact/4dRwM1jY1EytZtky4XbHR1
- **Mining overlay (card bars):** each character's ore hold bar drawn over the character's card in EVE-APM Preview, the thumbnail tool Kevin multiboxes with. Same look as the Mining Supervisor bar: compressed ore purple first, the rest green, yellow from the alert level, red when full, white mark at the alert level. The bar sits in the card's bottom-left corner, from 3 px inside the left edge to half the card's width, 6 px high and 4 px above the bottom, so it stays clear of APM's system name in the bottom-right. Bar only, no percentage number (Kevin's choice). Characters that aren't tracked miners (no hold size, no session) get no bar.
  - **Finding the cards:** EVE-APM Preview 0.9.9 (`EVEAPMPreview.exe`, Qt 6) makes one top-most tool window per card, titled `EVE - <character>`, class `Qt6101QWindowToolSaveBits`, 180 × 101 px on Kevin's PC. It lays a second click-through window titled `EVE-APM Preview` over each card for its labels; Athena ignores those. The EVE clients' own windows carry the same `EVE - <character>` titles, so the title alone is never enough. `EnumWindows` checks each visible window in this order: 1) the **window class** must start with `Qt` and contain `QWindowTool` (the `6101` is APM's Qt version, 6.10.1, and changes when APM updates, so it is never hardcoded); 2) the title must start with `EVE - `; 3) only then is the owning process confirmed as `EVEAPMPreview.exe` (`GetWindowThreadProcessId`, `OpenProcess` with `PROCESS_QUERY_LIMITED_INFORMATION`, `QueryFullProcessImageNameW`). Because the class check comes first, Athena never opens a handle to an EVE client process. The geometry comes from `GetWindowRect`.
  - **Matching:** APM can rename cards (Kevin's profile uses names like `Noa Askari [Mining]`), so a card belongs to a character when its title *contains* the character name, case-insensitive, never by equality. When several names fit, the longest wins.
  - **One window:** a single borderless, transparent, always-on-top, click-through eframe viewport (`show_viewport_deferred` with `with_transparent`, `with_always_on_top`, `with_mouse_passthrough`, `with_taskbar(false)`, never activated) covers the area the cards span and draws all bars. One viewport means one GPU surface, not one per character. A deferred viewport's callback gets only a `&Context`, no window handle, so Athena finds its own overlay `HWND` with `EnumThreadWindows` on the UI thread, matching the viewport's unique title (for example `Athena card bars`). That handle is what the z-order and style calls below use.
  - **Following the cards without polling:** `SetWinEventHook` (out of context, filtered to APM's process id) reports when a card moves, shows, hides, is created, destroyed or renamed; a 5 s safety check catches anything missed. The overlay hides when APM hides its thumbnails. Because APM's cards are also top-most, Athena re-asserts its z-order (`SetWindowPos` with `HWND_TOPMOST` and `SWP_NOACTIVATE`) after card events; that costs no redraw. Physical pixels are turned into egui points with the monitor's scale (Kevin's four 1080p screens are at 100%).
  - **Repaints:** only when a hold changes or a card moves.
  - **Toggle:** "Card bars" in the Mining Supervisor header and Settings, state saved in `mining.toml`. No hotkey (Kevin's choice).
  - **EULA:** Athena reads only APM's window titles and positions. It never reads from, captures or sends anything to the EVE client.
- **Intel popup:** a small always-on-top window that does not exist until an intel alert fires, then shows the same alert as the map banner (system, jumps, the pilots it is close to, ships, reporter, time) with the same red (loud) or orange frame. It never takes focus from EVE: it opens with `with_active(false)`, and Athena sets `WS_EX_NOACTIVATE` on its `HWND` (`SetWindowLongPtrW`, handle found the same way as the card-bar overlay's), so clicking or dragging it doesn't activate it either. It shows even while Intel sounds are muted (Kevin's choice: mute is about sound). Drag it by its grip to move it (`ViewportCommand::StartDrag`); the position is saved in `intel.toml`. It closes after a set time (default 5 s, changeable in Settings, 0 keeps it; Kevin's choice) or on ✕; a newer, closer report replaces it by the banner's rule. Settings: on/off, only for loud alerts, hide-after time, "Show popup to move it", "Reset position".
- **Cost:** expected about 10 MB RAM for the overlay window and near 0% idle CPU. PR 1 measures it on Kevin's PC and reports the numbers in the PR.
- **Risk checked first:** whether eframe keeps drawing a deferred viewport while Athena's main window is minimized. PR 1 proves this before the rest is built on it.
- **New dependency:** none. `windows-sys` gains two features: `Win32_UI_Accessibility` (for `SetWinEventHook`) and `Win32_System_Threading` (for `OpenProcess` and `QueryFullProcessImageNameW` in the card finder). `EnumWindows`, `EnumThreadWindows`, `GetWindowRect`, `SetWindowPos` and `SetWindowLongPtrW` are already covered by `Win32_UI_WindowsAndMessaging`.
- **Notes for build PR 1** (from the plan review):
  - **Transparency:** eframe has one app-wide `clear_color` for every viewport (default dark grey, alpha 180). Athena returns fully transparent `[0.0; 4]`, and the overlay uses a frameless, transparent panel, or it shows as a grey box over the cards. Transparency of a child viewport on glow takes a special path on Windows, so PR 1 proves the overlay is really see-through, not only that it draws while minimized.
  - **Minimized:** `show_viewport_deferred` must be called every parent frame or the viewport closes. Athena calls it from `App::logic()`, which keeps running while minimized (eframe then repaints the root about every 100 ms, fine for bars). The deferred callback must be `Send + Sync + 'static`, so the bar data is a small shared snapshot (`Arc<Mutex<…>>`).
  - **`SetWinEventHook` plumbing:** its callback has no user-data pointer, so events reach the overlay through a `static` sender (`OnceLock<Sender<…>>`). The hooking thread must pump messages (the winit UI thread does). An APM restart gets a new process id, so the 5 s safety check also re-hooks. `EVENT_OBJECT_LOCATIONCHANGE` fires many times while a card is dragged, so those events are coalesced before a repaint.
- **Done (PR 1):** `src/overlay/` holds the card finder and the overlay window, with a debug switch in Settings › Diagnostics that outlines each card found and shows the cards, the overlay's frame count and its last draw time. Changes from the notes above, found while building it:
  - The finder runs on its own thread with its own message loop (`MsgWaitForMultipleObjects`), not on the UI thread. The event hooks, the 5 s safety check, re-hooking after an APM restart and the coalescing of move events (30 ms) all live there, and the hook callback only sets a thread-local flag. The same scan also finds Athena's overlay window by its title among its own process's windows, so no `EnumThreadWindows` is needed.
  - eframe can only make a window during a full frame of the main window, and while Athena is minimized it runs only `logic()`. So the overlay window is made once, hidden, when it is switched on, and kept from `logic()`. From then on the finder thread shows it (`SW_SHOWNOACTIVATE`), hides it when there are no cards, moves it over the cards in physical pixels and puts it back on top (`SetWindowPos` with `HWND_TOPMOST`, `SWP_NOACTIVATE`, `SWP_ASYNCWINDOWPOS`). The egui side never sends it a position. Besides card events, a change of the foreground window also re-asserts the z-order.
  - winit makes a click-through window "layered", and Windows doesn't show a layered window until its layer opacity is set, so the finder calls `SetLayeredWindowAttributes` once (opaque; the see-through parts are the transparent pixels). It also adds `WS_EX_NOACTIVATE` and `WS_EX_TOOLWINDOW` (no Alt+Tab entry).
  - Tested under Wine with a stand-in `EVEAPMPreview.exe` (two cards, an APM label window and an EVE client window with the same title): only the two cards are found, the outlines follow a moved card, disappear while APM hides its cards and come back, and they keep drawing while Athena is minimized. Wine delivers no window events from other processes to the hook, so there everything ran on the 5 s safety check; how fast the hooks react has to be seen on Windows. Wine also can't show per-pixel transparency, so whether the overlay is see-through, and its RAM and CPU cost, still have to be checked on Kevin's PC.
- **Done (PR 2):** the card bars (`src/overlay/bars.rs`). Modules hand bars to the overlay through `Module::card_bars()` (called before every frame; the overlay repaints only when the bars change), and the overlay's status reaches them through `ModuleContext::overlay`. The Mining Supervisor gives one bar per tracked character that isn't hidden on the Live view, with the Live view's colours and the same stretch-to-full rule when EVE says the hold is full. "Card bars" sits on the right of the Mining header (on Windows only), and Mining › Settings has the mockup's "Mining overlay" box: the switch, the bar height (`card_bar_height_px`, 6 px by default, 2 to 20) and "Found N cards · M matched to miners". The mockup's "last checked just now" is left out: it would need a repaint every few seconds to stay true. The switch (`card_bars` in `mining.toml`) is off by default, so nobody without APM gets an overlay window.
- **Done (PR 3):** the intel popup (`src/overlay/popup.rs`), with the mockup's "Intel popup" box in Intel › Settings: on/off (`popup`, on by default), "Only for close alerts (loud range)" (`popup_only_loud`), "Hide after N s" (`popup_hide_secs`, 5 by default, 0 keeps it until ✕), "Show popup to move it" and "Reset position" (`popup_position` in `intel.toml`). ### Step 6: Dotlan map layout
The Intel map's `position2D` layout looks distorted next to Dotlan's clean, grid-aligned region maps, so the map takes its positions from Dotlan instead. Research and a side-by-side comparison of Athena's current layout, an own grid prototype, Dotlan and SMT: https://claude.ai/artifact/2nWZRD8NKYXaLLfMDGoo9s
- **Source checked (2026-11-09):**
  - **Dotlan:** each region map is an SVG at `https://evemaps.dotlan.net/svg/<Region>.svg`, with spaces in the name written as `_`. Every system is a `<use id="sys<systemID>" x=".." y=".." width="62.5" height="30">` box on a 1024 × 768 canvas. Systems of neighbouring regions that it connects to by gate are drawn at the edges with their own `sys<id>` boxes. All 68 regions in `static.sqlite` exist (known space, Pochven, Zarzakh as `Yasna_Zakh`, the new high-sec region Exordium and the Jove region UUA-F4), and every one of the 5,268 systems has a box in its own region's map. All 68 files together are about 5.4 MB. The layouts are stable: Branch is still identical to a 2018 copy.
  - **rnett/dotlanmaps** (a 2018 JSON copy of Dotlan, 64 regions, no Pochven, Zarzakh or Exordium) and **SMT** (MIT, but its layouts were converted from Dotlan's SVGs in 2022 and hand-edited since; it lacks Exordium and UUA-F4) are not used, because Dotlan itself is complete and current.
  - **Rights:** Dotlan's maps are "© Wollari, Daniel Hoffend", and the site states no reuse terms. Kevin decided that no permission is needed because Athena is a tool for him alone. So the Dotlan files are **never committed** to the repo. CI downloads them while building, and they end up only as positions inside `static.sqlite` in Kevin's zip. **If Athena is ever shared, for example with his corp, ask Wollari first** (in-game mail to Wollari), or switch back to the own grid layout from the comparison above. The README credits "Map layouts: DOTLAN EveMaps by Wollari" and carries CCP's standard copyright notice. Athena has no About box yet; when one comes, it gets the same two lines.
- **Getting the files:** the xtask learns `cargo xtask sde <sde zip> [<out file>] [--dotlan <folder>]` and `cargo xtask regions <sde zip>`, which prints the Dotlan file name of every region with gates (from the SDE's `mapRegions.jsonl`, so new regions are picked up on their own). A small PowerShell script, `xtask/dotlan.ps1`, takes that list and downloads each missing file into a `dotlan/` folder, one after another about a second apart, with the user agent `Athena (github.com/Razor170/Athena)` (never an email). Normally it fetches only the files that are missing, so a region that a new SDE adds is fetched even when the cache was found. With `-Refresh`, which the workflow passes when this month's cache key missed (`cache-hit != 'true'`), it downloads every file again and keeps the old copy only when a download fails.
  - **CI:** there is no separate release workflow; the `build` job in `ci.yml` makes `static.sqlite` on every PR and every push to main, so the download step runs there, guarded by a cache. The key is `dotlan-<year>-<month>` with `restore-keys: dotlan-`, so a new month starts from last month's files and refreshes them, and a Dotlan outage leaves last month's files in place. Only pushes to main save the cache (`actions/cache/restore` on PRs, `actions/cache/save` on main), because GitHub doesn't share a PR's cache with main or other PRs; a PR at the start of a month may still download the 68 files once (68 requests, a second apart), which is fine.
  - If a download fails, the cached file stays. With no file for a region at all, that region falls back to `position2D` with a warning, so a Dotlan outage never breaks a build.
  - The Linux coding sandbox has no `pwsh`, so the script can only run in CI and on Kevin's PC. In the sandbox the tests use the hand-written sample, and real files for screenshots are fetched with `curl`. The PR says so instead of claiming the script was tested there.
- **Reading the files:** the xtask finds each `<use id="sys` tag and reads its `id`, `x` and `y` attributes with plain string search. It needs nothing else from the SVG, so no new crate is added (no XML or regex crate). Positions are matched by system ID, never by name. A system inside the region with no box (for example after a patch adds systems before Dotlan has them) uses its `position2D` relative to its gate neighbours, and the xtask prints which ones did.
- **Placing:** a system's dot goes at the left of its Dotlan box (box x + 6, box y + 10), so the label to its lower right sits where Dotlan's box was. Athena's labels are wider than Dotlan's boxes because they also show security ("X7R-JW -0.4"), so x is stretched by about 1.5 and y by about 1.1; at that scale 20 of 68 regions still have touching labels (82 pairs), and the existing nudge pass separates those. The exact factors get tuned in the PR with screenshots. **Neighbour-region systems** (the hollow dots) use the position Dotlan gives them on the edge of this region's map. A box counts as a neighbour only when the SDE has a gate to it from this region, and when Dotlan has no box for a neighbour (for example a new gate), today's rule applies: 64 points out from the system it connects to. Which region a system belongs to always comes from the SDE, never from which SVG its box is in. Gate lines stay straight lines between dots, as now; Dotlan's line colours are not copied.
- **App:** no change. `static.sqlite` keeps the same tables and columns (`systems.map_x/map_y`, `region_borders`), so the map widget, Follow, tags, alerts, the kills tint and the Dotlan/zKillboard links work as they do. RAM and CPU stay the same, because only the numbers inside the file change. The schema version stays at 2.
- **Tests:** unit tests for the SVG reading (a small hand-written sample file, not a real Dotlan file, since those aren't committed), the placing and the fallback. When the files are there but give fewer than 95% of the systems in their regions a position, the build fails (regions whose file is missing don't count, so an outage never fails it), so a changed Dotlan format can't silently bring back the old map. The build also fails when a region's file exists but gives no boxes (a format change on one page, or an HTML error page saved as `.svg`), since one broken region is under 2% of all systems. Only a missing folder (Dotlan down and no cache) just warns. The xtask writes `map_layout` (`dotlan`, `position2d` or `mixed`) into the existing `meta` table, so the zip shows which layout it got without a schema change. The PR shows screenshots of Branch, Delve, The Forge and Pochven, old and new.
- **Build order:** one PR: download step, xtask reading and placing, fallback, credits and tests.
- **Done (2026-11-09):** `xtask/src/dotlan.rs` reads the SVGs, `map.rs` places the systems, `xtask/dotlan.ps1` downloads, and `ci.yml` caches the `dotlan` folder. The stretch stays at 1.5 × 1.1: with the SDE of 2026-11-04 all 5,268 systems are on Dotlan's maps, and the nudge pass moves 267 of them (in 35 regions) by more than a point.
